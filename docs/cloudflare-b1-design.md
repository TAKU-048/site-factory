# 段階B1：ローカルで完成させるフォーム・公開準備

状態：2026-10-19提案。ユーザー承認後に実装する。段階Aは独立したサイト生成まで完成。B1では受付・保存・通知再試行と公開候補の作成をローカルで動かし、実アカウント接続はB2へ分ける。

## 提供する動作

1. 同一サイトの/api/contactへ送信し、入力・Turnstile検証を通った問い合わせと通知待ちレコードを顧客別D1に保存する。
2. 保存成功後に受付番号を返す。表示は「お問い合わせを受け付けました。受付番号：…」。メール到達を約束する表示にしない。
3. 顧客の固定メール宛てへ通知する。事業者の認証済み送信元を使い、入力メールは検証後にReply-Toだけへ設定する。問い合わせ者への自動返信は標準では付けない。
4. 通知障害は保存内容から再試行し、結果が不明なものは要確認として管理一覧に出す。
5. ソース・素材・設定・ビルド成果物をまとめた公開候補を作成し、内容が変わると以前の承認を使えなくする。

## 境界と構成

Astroの静的出力＋顧客別Worker／D1。通常ページはStatic Assetsから配信し、/api/*だけWorkerを先に起動する。APIにHTMLを返すSPAフォールバックは使わない。静的404、API404、API405を分ける。

B1のHTTP通信先はローカル検証サーバーだけ。Turnstile・Resendは注入可能なテスト用アダプターで成功・失敗・タイムアウトを再現する。実装する本番アダプターには実キーを設定せず、試験中は外部へのfetchを拒否する。ブラウザからの外部Turnstileスクリプト読込もB1では行わない。

顧客専用のコピーへ明示適用し、既存顧客を一括で書き換えない。秘密情報、問い合わせ本文、通知先を公開JSON・public・納品サイトへ混入させない。顧客向けログイン画面は作らない。

## 入力と不正送信対策

- リクエストはUTF-8 JSON、ストリームを最大32KiBで打ち切る。Content-Lengthの申告値だけに頼らない。
- 設定された項目のみ最大10項目。必須nameは100文字、emailは254文字、messageは5,000文字。任意項目は1,000文字。メール・改行を含むヘッダー値を検証し、HTMLメールにはエスケープする。
- Originは設定済みの正規URLと一致必須。公開サイト名を入力値で切り替えない。通知先・DBはサーバー設定で固定する。
- Turnstileはサーバー検証に加えてhostnameとaction=contactを照合。期限切れ・再利用・障害時は新規保存せず、入力内容を残して再操作を案内する。
- 本番用のレート制限アダプターとローカル偽物を分ける。初期値はIP由来の短期ハッシュにつき60秒5回。IP本文は保存しない。制限拒否は429。これは地域分散環境で完全な全世界合算上限を保証するものではない。
- local／productionを明示し、ローカルの認証省略アダプターを本番設定で選べば起動を拒否する。

## 保存と二重送信

問い合わせIDはランダムUUID。別にブラウザが生成するrequestIdと受付内容のハッシュを保存し、requestIdに一意制約を置く。問い合わせとoutboxをD1の同一バッチで原子的に保存する。

同じrequestId・同じ本文の再送は既存の受付番号だけを返す。異なる本文なら409とし、新しい操作を案内する。返す情報は受付番号だけで本文は含めない。既存受付の照合を新しいTurnstile検証より先に行い、一度検証済みの同じ送信をトークン再利用で失敗させない。requestIdは推測困難なUUIDを要求する。DB失敗は503で、受付成功を返さない。

## メール通知と再試行

状態：pending → sending → accepted。deliveredはB2で署名検証済みの配送イベントを取り込んだ場合だけ。失敗はretrying／failed／unknownに分ける。acceptedをdeliveredと表示しない。

原子的な期限付き取得で同時実行を制御する。通知内容とIdempotency-Keyは最初の試行から固定。初回後の再試行は1・5・30・120・360・720分後（初回時刻からの経過）とし、429のRetry-Afterがあれば24時間未満の範囲でそれより早く再試行しない。恒久的4xxは停止する。タイムアウトや送信後DB更新失敗も同じキーで照合する。

Resendの重複防止キーは24時間保持される。その境界を越えた不明案件はunknownとして自動再送を止める。完全な一度限りの配送を保証せず、DB復元後も過去のメールを無条件に再送しない。ローカル試験で送信前後のクラッシュを再現する。

管理一覧は本文なしの件数・最終処理時刻・要確認理由だけを表示する。B1では常駐監視・定期自動起動を設定せず、再試行処理をローカルの手動コマンドで検証する。メール通知・本番Cronの有効化はB2で確認する。

## フォームと公開候補

未接続の既存デモは送信不可のまま。B1用検証サイトのみ接続し、送信中・成功・入力エラー・再試行・障害を実物確認する。成功後に本文を消し、失敗時は残す。エラー概要へフォーカスを移し、aria-live、48px操作領域、focus-visible、360／375pxを確認する。問い合わせ内容をlocalStorageへ保存しない。

公開候補は一意の新規ディレクトリへ作成する。ソース・依存ロック・静的ビルド・Workerバンドル・非公開運用設定をSHA-256で一覧化し、秘密値自体は含めない。秘密値変更も承認のやり直し対象にするため、公開しない管理記録のsecretRevisionを含める。revisionは自己申告なので、実接続時に設定実物との照合が別途必要。

B1の候補はnoindex、robots遮断、デモ表示を維持する。B2では本番設定で候補を新しく作り直してから承認する。承認後の再ビルドやファイル変更は新しい候補扱い。B1にはリモートdeployコマンドを実装しない。

## B2・B3へ引き継ぐ条件

B2：ユーザー指定アカウント・検証先で、固定受信者へのテスト送信、実際のDNS／SSL／既存MX、Turnstile、Resend署名検証Webhook、HTTP応答、アクセス制限、使用量を実地確認する。プレビューのnoindexはアクセス制御にならないためCloudflare Access等を別途設定する。共有Webhookはmessage IDと顧客の対応を照合してから顧客別処理へ渡す。Turnstile無料枠のグループ共有・秘密の影響範囲も実アカウントで確定する。公開・課金・DNS変更・送信には事前承認を得る。

B3：独立した暗号化バックアップの保存先、鍵の保管、復元試験、問い合わせ保持期間を決める。提案値は問い合わせ90日・運用ログ7日。自動削除は保持方針の明示承認まで実装・有効化しない。D1 Time Travelは同一サービス内の復旧で、独立バックアップの代用にしない。
